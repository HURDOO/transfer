# 아키텍처 결정 기록

## 2026-07-22: 단일 Node 프로세스와 SQLite3 메타데이터

- 상태: 승인
- 맥락: 사용자가 메타데이터 DB로 SQLite3를 지정했다. Raspberry Pi에서도 별도 DB 서비스나 npm 네이티브 애드온 빌드 없이 실행되어야 하고, 6자리 코드 유일성과 공유·파일 메타데이터를 트랜잭션으로 묶어야 한다.
- 결정: Vite로 만든 React SPA와 Fastify API를 한 pnpm 패키지로 구성한다. production은 Fastify가 SPA도 제공한다. Node 24 LTS 내장 `node:sqlite` 드라이버로 SQLite3 파일에 메타데이터를 저장하고, 대용량 파일 본문은 같은 볼륨의 UUID 경로에 둔다.
- 고려한 대안: `sqlite3`·`better-sqlite3` npm 네이티브 애드온, JSON 메타데이터, 별도 PostgreSQL 서비스.
- 결과와 트레이드오프: UNIQUE·외래키·트랜잭션과 향후 목록 쿼리를 확보하면서 ARM용 별도 바이너리 의존성을 피한다. 대신 Node 내장 SQLite API가 release candidate인 동안 Node 24.15 이상 LTS patch를 고정하고 업그레이드 호환성을 확인해야 한다.

## 2026-07-22: 공개 업로드는 인증 정책 결정 전 보류

- 상태: 2026-08-05 결정으로 대체됨
- 맥락: 6자리 수령 코드, 최대 1 GiB 익명 업로드, 무기한 만료를 그대로 공개하면 추측·디스크 고갈·불법 콘텐츠 악용 위험이 있다.
- 결정: 개발 편의를 위해 기본 바인딩을 `0.0.0.0`으로 변경해 LAN의 다른 기기에서 접근할 수 있게 한다. 인터넷 공개 운영 전에는 운영자 전용 업로드 인증, 디스크 quota, TLS와 요청 제한을 결정한다. 로컬 전용 실행은 `HOST=127.0.0.1`로 명시한다.
- 고려한 대안: 지금부터 계정·비밀번호 도입, 아무 보호 없이 공개.
- 결과와 트레이드오프: 핵심 송수신 경험은 바로 검증할 수 있지만, 현재 결과를 그대로 인터넷에 노출해서는 안 된다.

## 2026-08-05: 익명 송수신 유지, 배포 시스템은 후속 작업

- 상태: 승인
- 맥락: `옮기기`의 의도는 로그인 없이 파일과 텍스트를 올리고 코드·링크로 받는 것이다. Docker와 공개 배포 체계는 별도 작업으로 아직 구축 중이다.
- 결정: 생성·조회·다운로드 API와 웹 흐름에 사용자 로그인이나 운영자 전용 업로드 인증을 추가하지 않는다. 익명 송수신을 제품 동작으로 유지한다. Docker 이미지, reverse proxy/TLS, quota, 공개 노출과 악용 방지는 후속 배포 시스템 범위로 미룬다. 이 결정은 2026-07-22 결정의 `운영자 전용 업로드 인증` 선행 조건을 대체한다.
- 고려한 대안: 운영자만 업로드하도록 로그인 또는 토큰을 도입, 서비스 전체를 프록시 인증으로 보호.
- 결과와 트레이드오프: 링크를 받은 사람이 별도 계정 없이 바로 주고받는 경험은 유지된다. 대신 6자리 코드는 비밀키가 아니며, 공개 인터넷에 배포할 때는 인증과 별개로 디스크 quota, 요청 제한, TLS, 관측과 악용 대응을 배포 계층에서 마련해야 한다.

## 2026-08-06: 실시간 본문은 WebRTC로 직접 전송

- 상태: 승인
- 맥락: 브리프는 서버에 기록을 남기지 않는 1:1 공유를 MVP 이후 기능으로 명시한다. 배포 시스템과 별개로 앱 계약과 UI를 먼저 만들 수 있어야 한다.
- 결정: 실시간 세션은 10분 TTL의 6자리 코드, 임의 피어 토큰, 한 명의 수령자와 SDP·ICE 신호 큐만 Fastify 프로세스 메모리에 둔다. 본문은 WebRTC 데이터 채널로 직접 보내고 수령 확인도 같은 채널로 돌려준다. 첫 단위는 최대 1 MiB 텍스트다. 추가 WebSocket 의존성 대신 750ms REST polling을 사용하고, ICE 서버는 `LIVE_ICE_SERVERS` 환경변수로만 주입하며 기본값은 빈 배열이다.
- 고려한 대안: WebSocket 시그널링, 서버를 통한 비저장 스트림 릴레이, 공개 STUN 하드코딩, 처음부터 파일 청크와 재개까지 구현.
- 결과와 트레이드오프: 서버의 SQLite와 파일시스템에는 실시간 본문이 남지 않고 현재 단일 프로세스 구조를 유지한다. 서버 재시작 시 라이브 세션은 사라지고 polling 지연과 요청 비용이 있다. WebRTC 전송은 DTLS로 암호화되지만 상대 신원을 별도로 검증하지 않으며, 제한적인 NAT·방화벽에서는 운영 TURN이 없으면 연결되지 않을 수 있다.

## 2026-08-06: 실시간 파일은 순차 청크와 브라우저 Blob으로 수신

- 상태: 승인
- 맥락: 실시간 모드를 텍스트 전용에서 여러 파일과 텍스트 공유로 완성하되 1 GiB 파일을 보내는 쪽 메모리에 한 번에 읽거나 WebRTC 내부 버퍼에 무제한 쌓지 않아야 한다. 수령 쪽은 모바일을 포함한 표준 브라우저에서 별도 네이티브 파일시스템 권한 없이 다운로드할 수 있어야 한다.
- 결정: 텍스트와 최대 50개 파일의 메타데이터를 매니페스트로 먼저 보내고, 파일을 순서대로 64 KiB 청크로 읽어 전송한다. 보내는 쪽의 대기 버퍼는 최고 1 MiB, 재개 기준 256 KiB로 제한한다. 받는 쪽은 순서·파일별 크기·합계 1 GiB·파일명 512바이트를 검증하고 완료 파일을 Blob URL로 제공한다. 완료·수령 확인·양쪽 취소는 같은 데이터 채널의 버전 1 제어 메시지로 주고받는다.
- 고려한 대안: 파일 전체를 `arrayBuffer()`로 읽어 한 메시지로 전송, 서버 비저장 HTTP 릴레이, File System Access API 전용 저장, 중단 지점 영속 재개.
- 결과와 트레이드오프: 보내는 쪽 작업 메모리와 WebRTC 대기열은 작게 제한되고 모든 주요 브라우저에서 개별 다운로드가 가능하다. 반면 수령 완료 파일은 탭을 닫기 전까지 합계 최대 1 GiB가 브라우저 메모리를 사용할 수 있으며, 연결 중단 뒤 이어받기와 안전 번호 기반 상대 확인은 후속 범위다.

## 2026-08-07: 받기는 단일 코드 입력과 통합 코드 공간 사용

- 상태: 승인
- 맥락: 보내는 쪽은 보관 여부를 의도적으로 골라야 하지만, 받는 사람에게 같은 선택을 다시 요구하면 코드를 받았어도 전송 방식을 알아야 한다. 저장형과 실시간이 별도로 6자리 코드를 발급하면 자동 판별 시 같은 활성 코드가 두 방식에 동시에 존재할 수도 있다.
- 결정: 받는 홈은 입력란 하나만 보여 주고 `GET /api/codes/:code` 결과로 저장형 또는 실시간 수령 경로를 자동 선택한다. 저장형 저장소와 메모리 실시간 세션은 코드 생성 때 서로의 활성 코드를 확인해 같은 코드를 발급하지 않는다. 방식이 포함된 직접 링크는 기존 경로를 유지한다.
- 고려한 대안: 받는 사람도 보관·실시간 탭을 먼저 선택, 같은 코드가 겹치면 한 방식 우선, 코드 접두사나 자릿수 변경.
- 결과와 트레이드오프: 수령자는 코드만 알면 되고 기존 링크도 호환된다. 두 저장소를 한 프로세스에서 조정하므로 현재 단일 프로세스 구조에는 맞지만, 다중 인스턴스로 확장할 때는 공유 원자적 코드 예약소가 필요하다.

## 2026-08-07: 보낸 기록은 브라우저 로컬, 삭제 권한은 공유별 관리 키

- 상태: 승인
- 맥락: 로그인 없는 송수신을 유지하면서 사용자가 자신이 보낸 항목을 확인하고 보관 시간이 끝나기 전에 서버 파일을 지울 수 있어야 한다. 서버 전체 공유 목록을 익명 API로 노출하면 코드 추측보다 훨씬 큰 정보 노출이 되고, 계정을 추가하면 합의된 익명 흐름을 바꾼다.
- 결정: 성공한 전송의 요약 기록은 현재 브라우저 IndexedDB에만 둔다. 저장형 생성마다 URL-safe 32자리 관리 키를 한 번 발급하고 서버는 SHA-256 해시만 스키마 버전 2의 nullable 열에 저장한다. 유효한 Bearer 키를 받은 삭제 API만 공유와 파일을 즉시 제거한다. 만료·삭제 기록은 코드와 원본 키를 지우며 실시간 성공 기록에는 코드·피어 토큰을 저장하지 않는다.
- 고려한 대안: 인증 없는 서버 전체 목록 API, 사용자 계정과 로그인, 6자리 코드만으로 삭제, 서버 세션 쿠키, 기록 없이 생성 결과에서만 삭제.
- 결과와 트레이드오프: 계정 없이 현재 기기에서 보낸 공유를 관리하고 서버 목록 노출을 피한다. 삭제 관리 키는 고급 기능으로 취급해 일반 생성 결과가 아니라 `/history`의 활성 기록에서만 펼쳐 보거나 복사한다. 다른 브라우저·기기와 기록이 동기화되지 않고 브라우저 데이터를 지우면 삭제 권한을 잃는다. 기존 버전 1 공유는 마이그레이션 뒤에도 유지되지만 소급 관리 키가 없어 API로 즉시 삭제할 수 없다. 버전 2 DB는 구버전 애플리케이션에서 열 수 없으므로 배포 전 전체 저장 루트 백업이 필요하다.
