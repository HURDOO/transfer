# 아키텍처

상태: 저장형 MVP와 실시간 파일·텍스트 전송 기준

## 기술 스택

- 클라이언트: React 19, TypeScript, Vite 8, 별도 UI 프레임워크 없는 CSS
- 서버: Node.js 24.15 이상, Fastify 5, `@fastify/multipart`
- 저장소: Node 내장 `node:sqlite`를 통한 SQLite3 메타데이터와 같은 로컬 볼륨의 원본 파일
- 검증: ESLint, TypeScript, Vitest, Vite production build, 실제 브라우저
- 패키지 관리자: pnpm

개발 중에는 Vite가 `/api`를 Fastify로 프록시한다. production build에서는 Fastify 한 프로세스가 API와 빌드된 SPA를 함께 제공한다.

## 시스템 구성

```text
브라우저 / API 클라이언트
        │ multipart 업로드 · JSON 조회 · 파일 스트림
        ▼
Fastify API ───────────────► 로컬 저장 루트
        │                    ├── transfer.sqlite3
        │                    ├── tmp/{공유 UUID}/files/{파일 UUID}
        │                    └── files/{공유 UUID}/files/{파일 UUID}
        ▼
React SPA (production에서는 같은 프로세스가 정적 제공)

실시간 보내는 브라우저 ◄── WebRTC 데이터 채널 ──► 실시간 받는 브라우저
          │           파일·텍스트 본문은 서버를 통과하지 않음           │
          └────── REST polling SDP·ICE 신호 ── Fastify 메모리 세션 ────┘
```

## 주요 모듈과 책임

- `shared/contracts.ts`: 만료 값, 업로드 제한, 코드 판별과 웹/API 공유 타입
- `server/share-store.ts`: SQLite 스키마·트랜잭션, 실시간 세션과 공유하는 코드 유일성, 만료 판정, 파일 경로 격리, 정리
- `server/app.ts`: 통합 코드 판별, multipart 스트리밍, API 라우트, 오류·요청 제한, production 정적 파일 제공
- `server/live-session-store.ts`: 저장형 공유와 공유하는 10분 TTL 라이브 코드, 피어 토큰, 단일 수령자와 메모리 신호 큐
- `server/live-ice-config.ts`: 운영자가 주입한 STUN/TURN JSON 검증
- `server/upload-request-signal.ts`: 프록시의 정상 요청 완료와 실제 중단을 구분하는 업로드 취소 신호
- `src/api.ts`: 브라우저 업로드 진행률, 통합 코드 판별과 조회 계약
- `src/share-history.ts`: 현재 브라우저 IndexedDB의 보낸 기록, 만료 상태 정리와 삭제 관리 키 보관
- `src/live-transfer.ts`: 트리클 ICE, WebRTC 데이터 채널, 흐름 제어와 송수신 생명주기
- `src/live-transfer-protocol.ts`: 파일 매니페스트·64 KiB 청크·완료·취소·수령 확인 프로토콜과 수신 조립
- `src/App.tsx`: 보내기, 코드 받기, 공유 결과·수령 화면과 로컬 기록장
- `src/styles.css`: 라이트·다크 토큰, 반응형 레이아웃, 축소 가능한 완료 애니메이션

## 데이터 모델

SQLite3의 `shares` 테이블은 공유 UUID, 고유한 6자리 코드, 생성·만료 시각, 선택 텍스트, 합산 바이트와 선택 삭제 관리 키의 SHA-256 해시를 저장한다. `share_files` 테이블은 파일 UUID, 공유 외래키, 원래 이름, 크기, MIME, 표시 순서를 저장한다. 외래키 삭제는 cascade하며 만료 시각 인덱스를 둔다. 스키마 버전 2는 버전 1 DB에 nullable 해시 열을 추가하며 기존 공유는 그대로 유지하지만 새 관리 키를 소급 발급하지 않는다.

파일 본문은 DB BLOB이 아니라 `files/{공유 UUID}/files/{파일 UUID}`에 둔다. 업로드 중에는 `tmp`에 쓰고 성공한 뒤 같은 볼륨 안에서 rename한다. 이어지는 SQLite `BEGIN IMMEDIATE` 트랜잭션이 공유와 파일 행을 한 번에 확정한다. 최초 스키마 생성도 트랜잭션으로 묶는다. 저장형과 실시간 코드 생성기는 서로의 활성 코드를 확인하고, 자체 UNIQUE 충돌과 함께 새 난수로 재시도한다. DB 반영 전 프로세스가 종료되어 생긴 고아 디렉터리는 시작 정리가 제거한다.

## 데이터 흐름

받는 홈은 `GET /api/codes/:code`로 활성 저장형 공유와 실시간 세션을 함께 조회한다. 응답의 `kind`가 `stored`면 `/s/:code`, `live`면 `/live/:code`로 이동한다. 직접 링크는 이 판별 단계를 생략한다.

1. 서버가 임시 공유 UUID 디렉터리를 예약한다.
2. multipart 각 파일의 안전한 표시명과 512바이트 이름 제한을 먼저 검사한 뒤 임시 파일 UUID 경로로 스트리밍하며 전체 바이트를 누적한다.
3. 만료값, 빈 입력, 텍스트 1 MiB와 공유 1 GiB 합산 제한을 검증한다. 멈춘 요청은 30분에 종료하고 임시 예약을 제거한다. 입력 스트림 `close`는 HTTP 본문이 완전히 수신되지 않은 경우에만 파일 파이프라인을 중단한다.
4. 임시 디렉터리를 최종 위치로 rename하고 SQLite 트랜잭션으로 코드·공유·파일 메타데이터를 확정한다.
5. 조회 시 형식·존재·만료를 확인한 뒤 공개 메타데이터만 반환한다. 열린 브라우저도 만료 타이머와 탭 재활성화 시각 검사를 통해 캐시된 내용과 코드 UI를 보관 종료 화면으로 교체한다.
6. 다운로드 시 같은 검사를 다시 수행하고 메타데이터에 기록된 ID만 스트리밍한다.
7. 생성 때만 원본 삭제 관리 키를 응답한다. 삭제 요청은 Bearer 키의 해시를 일정 시간 비교한 뒤 같은 공유 행과 파일 디렉터리를 제거하며, 공개 조회에는 키를 포함하지 않는다.

보낸 기록은 서버 목록이 아니라 브라우저별 `move-it` IndexedDB의 `sent-transfers` 저장소에 둔다. 저장형 성공 기록에는 파일명·텍스트 포함 여부·합계·시각과 활성 코드·원본 관리 키를 저장한다. 생성 응답을 받은 흐름은 원본 키를 IndexedDB에 즉시 기록하되 일반 결과 화면에는 렌더링하지 않고 `/history`의 고급 관리 영역에서만 표시한다. 만료나 즉시 삭제를 반영할 때 코드와 키를 제거한다. 실시간 성공 기록은 같은 요약 메타데이터만 저장하고 코드·피어 토큰은 남기지 않는다. 파일과 텍스트 본문은 IndexedDB에 복제하지 않는다.

실시간 파일·텍스트는 별도 흐름이다.

1. 보내는 브라우저가 메모리 세션을 만들고 6자리 코드와 보내는 쪽 임의 토큰을 받는다.
2. 첫 수령 브라우저가 코드를 참가 처리해 받는 쪽 임의 토큰을 받고, 서버는 보내는 쪽 큐에 준비 신호를 넣는다.
3. 두 브라우저는 750ms 간격 REST polling으로 SDP를 교환하고 ICE 후보는 수집되는 즉시 상대 큐로 보낸다. 토큰은 신호 큐의 방향과 세션 종료 권한만 식별한다.
4. WebRTC 데이터 채널을 열어 텍스트와 파일 매니페스트를 먼저 보낸 뒤 파일마다 시작 신호, 최대 64 KiB 이진 청크, 종료 신호를 순서대로 보낸다.
5. 보내는 쪽은 데이터 채널 대기 버퍼가 1 MiB를 넘으면 256 KiB 아래로 줄 때까지 파일 읽기를 멈춘다. 받는 쪽은 선언된 합계 1 GiB·50개·이름 512바이트 제한과 실제 청크 크기·순서를 다시 검증한다.
6. 받는 브라우저가 전체 조립 뒤 수령 확인을 돌려주면 양쪽이 메모리 세션 닫기를 요청한다. 보내는 쪽은 세션 정보를 클라이언트 상태에서도 제거하고 코드 없는 완료 화면으로 전환한다. 완료 파일의 Blob URL은 수령 화면이 열려 있는 동안만 유지한다. 만료나 서버 재시작 시 신호 상태만 사라진다.

## 인증과 보안 경계

- 첫 흐름은 로컬 익명 업로드·수령이다. 서버는 기본적으로 모든 인터페이스에 바인딩되어 LAN에서 접근할 수 있다. 인증·디스크 quota·TLS 없이 인터넷에 공개하지 않는다.
- 코드 소지자는 내용을 읽을 수 있다. 서버 운영자는 평문 파일과 텍스트에 접근할 수 있다.
- 삭제 관리 키 소지자는 해당 저장형 공유를 제거할 수 있다. 서버 DB에는 키 해시만 있지만 보내는 브라우저에는 활성 기간 동안 원본 키가 있으므로 XSS 방지 정책과 브라우저 프로필 접근 통제가 중요하다.
- 실시간 모드의 서버 운영자는 파일·텍스트 본문을 받지 않지만 피어 IP와 SDP·ICE 연결 메타데이터는 일시적으로 관찰할 수 있다. STUN/TURN 사업자도 연결 메타데이터를 볼 수 있다. TURN을 사용하면 암호화된 패킷은 중계되지만 본문 평문은 노출되지 않는다.
- 사용자 파일명은 경로로 쓰지 않고 제어 문자와 경로 구분자를 제거한 512바이트 이하 표시명으로만 보존한다.
- 생성과 조회에 메모리 기반 rate limit를 적용한다. 다중 인스턴스 운영 전에는 공유 저장소 기반 제한으로 교체해야 한다.
- production의 절대 URL은 신뢰할 수 있는 `APP_BASE_URL`로 고정한다. TLS와 외부 요청 크기 제한은 향후 리버스 프록시가 담당한다.

## 오류 처리와 관측성

- 알려진 입력·용량·부재 오류는 안정된 오류 코드와 상태로 응답한다.
- 예상하지 못한 오류만 서버 로그에 스택을 남기고 응답에는 내부 경로나 내용을 노출하지 않는다.
- 만료 공유는 조회 즉시 거부하고 안전하게 제거한다. 서버 시작 시와 주기적으로 만료·미완료 공유를 정리한다.

## 배포와 롤백

Node 24.15 기반 multi-stage Dockerfile은 잠금 파일로 의존성을 설치하고 빌드 결과와 production 의존성만 담은 `linux/arm64` 이미지를 만든다. 런타임은 읽기 전용 루트, `/tmp` tmpfs, capability 제거와 `no-new-privileges`를 전제로 하며 SQLite와 파일은 `/data` 한 곳에만 쓴다. `GET /healthz`가 컨테이너와 deployd 헬스 계약이다.

프로젝트의 `deploy.json`은 앱 ID `transfer`, 이미지 저장소 `ghcr.io/hurdoo/transfer`, 컨테이너 포트 3000, private 접근, `/data`, `large-upload`를 고정한다. Codex의 게시 도구는 이 계약과 immutable digest를 대시보드 핸드오프 JSON으로 만든다. 사용자가 승인하면 deployd가 정책 범위에서 Raspberry Pi 루프백 포트, `/srv/homelab/data/transfer` → `/data`, exact-host Nginx·인증서와 첫 릴리스를 자동 생성한다. 호스트 경로·포트·Compose·권한·비밀값은 프로젝트나 핸드오프가 지정할 수 없다.

이미지 롤백은 SQLite나 파일 상태를 되돌리지 않는다. 데이터 형식 변경 전에는 전체 데이터 루트 백업과 버전별 마이그레이션·복구 승인이 필요하다.

## 알려진 위험

- 6자리 코드는 총 100만 개라 추측 방지 수단이 아니다.
- Node 24의 내장 SQLite API는 release candidate 단계다. LTS patch를 고정하고 API 안정성 변경을 업그레이드 때 확인해야 한다.
- 애플리케이션의 1 GiB 제한과 별개로 공개 운영 시 프록시, 디스크 quota, 동시 업로드 제한이 필요하다.
- STUN만으로는 제한적인 NAT·방화벽을 통과하지 못할 수 있다. 공개 실시간 기능의 신뢰성에는 단기 자격 증명을 발급하는 TURN이 필요하다.
- 표준 브라우저 다운로드 호환성을 위해 완료된 실시간 파일은 수령 탭 메모리에 Blob으로 유지된다. 선언·검증 상한은 합계 1 GiB지만 저메모리 모바일에서는 큰 묶음을 나누어 보내는 편이 안전하다.
